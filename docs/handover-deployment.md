# Передача разработки после настройки деплоя

Состояние проверено 20 сентября 2026 года. Документ описывает выполненную
миграцию и ограничения для дальнейшей разработки. Постоянная инструкция
по эксплуатации находится в [README](../README.md).

## С чего начать агенту

1. Прочитать этот документ, README и применимые инструкции AGENTS.md, если
   они есть в своей рабочей копии. Этот handover не отменяет указания владельца.
2. Проверить `git status`, текущую ветку и remote. Получить актуальную `origin/main`
   через `git fetch origin`; сопоставить её со своей веткой и сохранить свои
   незакоммиченные изменения. Не делать безусловный reset или checkout поверх них.
3. Учесть изменения коммитов `fc9cb6f` и `b9af759`, прежде чем продолжать
   разработку по старой копии кода. Эти изменения уже работают в production.
4. Использовать Node.js 24 и выполнить `npm ci --ignore-scripts`,
   `npm run check`, `npm test`. Тестам не нужны настоящие секреты.
5. Продолжать согласованную с владельцем разработку. Получение handover само
   по себе не является заданием менять сервер или выполнять новый деплой.

**Каждый push в main, включая изменение только документации, запускает
production-деплой и перезапуск бота.** Для разработки использовать отдельную
ветку. Pull request в main выполняет проверки без деплоя. Слияние в main
тоже запускает деплой. Ручной запуск workflow деплоит только при выборе main.

## Изменения, которые разработчику нужно учесть

- `node-telegram-bot-api` обновлён с `0.66.0` до **`2.1.0`**; старые вызовы
  несовместимы. Сейчас используются `Api`, `InputFile`, `api.setWebhook({...})`,
  `api.sendMessage({chat_id, text})` и `api.sendChatAction({...})`.
- [index.js](../index.js) экспортирует `configuration` и `createApplication`
  для тестов с подставными API. Рабочий запуск выполняется через `main()`.
  `systemPrompt.js`, модель `openai/gpt-oss-120b` и назначение бота сохранены.
- Webhook перенесён с пути, содержащего токен, на `/telegram`. Запросы требуют
  `X-Telegram-Bot-Api-Secret-Token`; его значение выводится из токена бота внутри
  приложения. Отдельного GitHub-секрета для этого заголовка нет.
- `WEBHOOK_CERTIFICATE` обязателен. Файл читается до регистрации webhook;
  его публичная часть отправляется в Telegram. Ошибка регистрации останавливает
  приложение. Не возвращать вывод URL с токеном или сырых SDK-ошибок в журналы.
- `/healthz` обращается к Telegram и проверяет фактический webhook; при
  несовпадении или недоступности API возвращает 503. Это не проверка генерации
  Groq или доставки ответов. `GET /` — лишь простая проверка HTTP-сервера.
- `.github/workflows/keep-alive.yml` удалён. Взамен нет периодического пинга:
  постоянный процесс поддерживает systemd, health-check выполняется по запросу.
- История остаётся в памяти, сбрасывается при рестарте; в модель идут последние
  10 сообщений. Очереди по чатам и дедупликации update_id нет. Webhook отвечает
  200 до завершения обработки сообщения; durable-очередь не реализована.

## Где находятся настройки деплоя

| Файл | Назначение |
|---|---|
| [deploy.yml](../.github/workflows/deploy.yml) | Триггеры, проверки, секреты, доставка релиза и внешняя проверка |
| [activate.sh](../deploy/activate.sh) | Установка зависимостей, переключение current, restart, проверка и откат |
| [verify-apis.js](../deploy/verify-apis.js) | Проверка Telegram/Groq и снимок прежнего webhook перед переключением |
| [restore-webhook.js](../deploy/restore-webhook.js) | Попытка восстановления прежнего webhook при неудаче первого запуска |
| [debate-bot.service](../deploy/debate-bot.service) | Шаблон root-owned systemd unit |
| [nginx.conf](../deploy/nginx.conf) | Шаблон HTTPS reverse proxy |
| [bootstrap.sh](../deploy/bootstrap.sh) | Первичная настройка от root; не запускается обычным CI |
| [known_hosts](../deploy/known_hosts), [webhook.pem](../deploy/webhook.pem) | Публичные ключи для проверки SSH и TLS |
| [webhook.test.js](../test/webhook.test.js) | Проверки API v2, сертификата, авторизации webhook, health и диалога |

Repository secrets: `DEPLOY_SSH_KEY`, `TELEGRAM_TOKEN`, `GROQ_API_KEY`.
Их значения, содержимое `.env`, приватные ключи и снимки прежнего webhook
не включать в коммиты, сообщения или логи. Локальные файлы с токенами исключены
из Git и Docker-контекста. Секреты для сервера передаются workflow по SSH;
у каждого релиза свой `.env` с правами 600.

CI задаёт `WEBHOOK_URL=https://185.183.157.185`,
`WEBHOOK_CERTIFICATE=/etc/debate-bot/webhook.pem`, `HOST=127.0.0.1`, `PORT=3000`
и `REVISION=<SHA коммита>`. Приватный TLS-ключ находится только на сервере,
в `/etc/debate-bot/webhook.key`, root:root, 600. Не отключать проверки SSH/TLS.

**Не запускать локально `npm start` с production-токеном для обычной проверки:**
приложение регистрирует webhook при старте. Использовать тесты с подставными
API или отдельного тестового бота. `npm test` рабочий webhook не меняет.

## Права и границы автоматизации

Обычный деплой работает через SSH от `deploy`, не root. Пользователь владеет
`/srv/debate-bot` и устанавливает npm-зависимости без sudo. Привилегированные
операции доступны только через `sudo -n /usr/local/sbin/debate-deploy-admin`.
Для списка разрешённых действий: `... help`; для диагностики: `... bot-status`
и `... bot-logs`. Общего sudo, изменения пользователей/SSH и произвольной
записи в системные каталоги нет. Установка системных пакетов ограничена списком.

Обработчик и `/etc/sudoers.d/debate-deploy` созданы отдельно при подготовке
сервера: их установка не реализована в `bootstrap.sh`, а сам обработчик пока
не хранится в репозитории. Он сбрасывает счётчик аварий только службы бота перед
start/restart. Новый сервер нельзя полностью восстановить одним bootstrap.

CI не применяет изменения root-owned unit, Nginx, sudo или TLS-ключа. Правка
их шаблонов в репозитории сама по себе не меняет сервер; такие изменения
применяет администратор отдельно. `update-system` обновляет APT-пакеты,
но не установленный отдельно Node.js в `/opt/nodejs`.

При ошибке после переключения current скрипт пытается вернуть предыдущий
релиз и перезапустить службу. До переключения действующий релиз не трогается.
Если падает только последняя внешняя проверка из GitHub runner, workflow
становится failed, но уже активированный релиз автоматически не откатывается.
Восстановление после отката отдельно не проверяется скриптом на готовность;
фактический сбой и откат в production при настройке не моделировались.

## Оставшиеся вопросы и обслуживание

1. **Старый SnapDeploy нужно остановить у владельца.** Во время первого деплоя
   после успешной регистрации нового webhook Telegram снова показывал старый
   адрес SnapDeploy. После второго деплоя адрес правильный, это перепроверено.
   Требование сертификата блокирует запуск новой версии со старой конфигурацией,
   но сертификат публичный и не является эксклюзивным правом на webhook.
   Старый код или любой процесс с токеном по-прежнему может его изменить.
   Старый экземпляр агент не остановил и токен не отзывал.
2. **Сертификат истекает 20 сентября 2027 года в 12:02:36 UTC.** Автопродления
   нет. Нужны согласованное обновление серверного сертификата и публичной копии
   в Git, reload Nginx и повторная регистрация webhook. Bootstrap существующий
   сертификат не продлевает. Порядок обновления должен учитывать сертификат,
   закреплённый во внешней проверке CI; это отдельная операция обслуживания.
3. **Старые релизы сохраняются без автоматической очистки.** Контролировать
   место и после ротации секретов удалить ненужные старые `.env` и снимки
   `.webhook-before.json`, сохранив нужную возможность отката.
4. **Проверка диалога остаётся за владельцем/тестировщиком:** отправить сообщение
   боту, получить греческий ответ, проверить `/new`. Не считать health-check
   доказательством прохождения полного пользовательского сценария.

При дальнейших изменениях обновлять README и тесты. Перед разрешённым
production-push проверять код; после него сопоставлять SHA в Actions,
`/srv/debate-bot/deployment.json` и `/healthz`. Этот документ — снимок передачи,
а не постоянно актуальный список открытых задач: сначала проверить, что из
перечисленного уже сделано после указанной даты.
